## Why the frontends need their own plan

The parent plan classifies both UIs as **"static pass"** — `location = /healthz { return 200 'ok'; }` and done. That is correct for *liveness* and wrong as a complete answer, because it makes the probe report on the only part of these containers that cannot realistically fail.

Both UIs are configured at runtime by a `config.json` the chart renders from a ConfigMap (see rule F3 for the exact mechanism):

```yaml
# gitops/helm-values/apps/qr-manager-ui/base.yaml
    templates:
      config:
        file: config.json
        path: /usr/share/nginx/html/config.json
        subPath: config.json
```

The SPA cannot start without it — `src/main.tsx` in both apps awaits `loadRuntimeConfig()` and, on failure, replaces `#root` with an error box. So the live failure mode is:

1. ConfigMap missing, renamed, or its templated content is malformed (both files are generated by Jinja2 substitution of `{{ VAR_* }}` / `{{ SECRET_* }}` placeholders — a substitution that silently produces `""` yields valid JSON that fails validation in the browser).
2. nginx starts fine. `/healthz` returns `200 ok`.
3. kubelet marks the pod Ready. Endpoints gains it. Traefik routes to it. ArgoCD reports `Healthy`.
4. Every user gets a blank page or a red error box.

That is precisely the "green does not mean working" class the parent plan exists to close, and the parent plan's UI steps do not close it. **`qr-manager-ui` has no config validation of any kind today.** `homelab-dashboard-ui` accidentally has some — its custom entrypoint `jq`s `unifi.host` out of `config.json` and exits 1 if absent — but that is a side effect of needing the value for `proxy_pass`, not a deliberate health check, and it does not validate `unifi.apiKey`.

Second gap: nothing in either UI tells a *user* that the backend is down. `qr-manager-ui` surfaces `Error: Request failed with 503: ...` per page; `homelab-dashboard-ui` puts the raw message in the `StatusBar`. Neither is wrong, both are duplicated, and neither distinguishes "this request failed" from "the API is gone".

## What "health" means for a frontend

Three layers, with three different owners. Keeping them separate is the whole design.

| Layer | Question | Who consumes it | Mechanism here |
| --- | --- | --- | --- |
| **1 — Container** | Is nginx serving? | kubelet | `location = /healthz` |
| **2 — Boot correctness** | Is this container *capable* of serving a working app? | kubelet, indirectly — via the container refusing to start | validating initContainer, fail-fast |
| **3 — Session** | Can the app the user has loaded still reach its backend? | the human looking at the screen | request-driven status in the SPA |

Layer 2 is the one the parent plan skips, and it is where nearly all the value is. Layer 3 is not a Kubernetes concern at all, and conflating it with layers 1–2 is the classic mistake — see decision 3.

### Rule F1 — a static file server has no live/ready distinction

After boot-time validation there is nothing a readiness check could know that a liveness check could not. `qr-manager-ui` serves files from disk; there is no connection pool to exhaust, no event loop to wedge, no dependency to lose. One endpoint, used by all three probes, is the honest answer. Inventing `/readyz` that returns the same constant is noise.

### Rule F2 — never readiness-check the backend from the UI pod

If `qr-manager-ui`'s readiness probe hit `qr-manager-api`, then an API outage would delete the UI from Endpoints and users would get a Traefik `502` instead of an application that loads and says "the API is unavailable". The UI can still serve its shell, its assets, and its error state — it must stay Ready. This is the parent plan's rule 2 shared-fate trap in its most tempting form.

The same applies to `homelab-dashboard-ui`'s Unifi reverse proxy, which the parent plan already calls out.

### Rule F3 — the config is a boot-time input, not a runtime one

The `config.json` the container reads is **not** mounted from the ConfigMap directly. The chart's `templates:` key generates, per template, a ConfigMap holding a *Jinja2 source* plus an `objectiflibre/jinja-init` **initContainer** that renders it into an `emptyDir` (`…-tpl-out-<name>`), and it is that emptyDir the main container mounts (`deployment.yaml:56-108, 161-170`).

Two consequences:

- **The file cannot change under a running pod.** An emptyDir is populated once, by an initContainer, at pod start. Not "does not usually update" — it structurally cannot. So validating once, at pod start, is complete coverage.
- **The rendered result only exists inside the pod.** The ConfigMap holds `{{ VAR_* }}` / `{{ SECRET_* }}` placeholders; what those substitute to is invisible outside the pod. A substitution that silently yields `""` is therefore *only* detectable in-pod — which is the argument for validating there rather than in CI or a chart `helm unittest`.

This also means validation must run **after** jinja-init. That is automatic: all initContainers complete before the main container starts, so anything the nginx container's entrypoint does already sees the rendered file.

#### Stakater Reloader strengthens this, it does not weaken it

Reloader is landing shortly (`homelab` — `docs/superpowers/plans/2026-08-05-stakater-reloader.md`). It restarts a workload when its ConfigMap or Secret changes, and that plan **removes the chart's `checksum/config` annotation**, making Reloader the only restart mechanism — it names `qr-manager-ui` as needing the opt-in annotation for exactly that reason.

That changes nothing about the invariant above: Reloader does not mutate a running pod, it creates a new one. jinja-init re-renders, the entrypoint re-validates, and the file is again fixed for that pod's life.

What it *does* change is the stakes, in favour of this design:

- **Today**, a bad config edit sits harmless until something unrelated restarts the pod — possibly days later, surfacing at a time nobody connects to the edit.
- **With Reloader**, that edit triggers an **immediate, automatic, unattended rollout**. Without validation, the new pod boots, passes `/healthz`, goes Ready, and the old pod is torn down — a blank page shipped to users by a mechanism nobody was watching.
- **With validation**, plus `maxUnavailable: 0` / `maxSurge: 1`, the new pod `CrashLoopBackOff`s and the old pod keeps serving. The bad edit is contained at the moment it is made, and named in the pod log.

Automatic config rollouts and unvalidated config are a bad combination. Reloader supplies the first; this plan supplies the guard.

### Rule F4 — nginx's graceful shutdown is already correct; do not break it

Verified against the nginx and Kubernetes docs during planning:

- nginx master process: `SIGTERM`/`SIGINT` = **fast shutdown** (in-flight requests dropped), `SIGQUIT` = **graceful shutdown** (workers finish current requests first).
- The official `nginx` image sets `STOPSIGNAL SIGQUIT` for exactly this reason.
- Kubernetes takes the stop signal from the image's `STOPSIGNAL` (containerd/CRI-O), defaulting to `SIGTERM` only when the image declares none. Overriding it via `lifecycle.stopSignal` needs the `ContainerStopSignals` feature gate plus `spec.os.name`, and is **not needed here**.

Both images inherit `STOPSIGNAL SIGQUIT` from `nginx:1.29-alpine`, and in both nginx ends up as PID 1 (`qr-manager-ui` via `CMD`, `homelab-dashboard-ui` via `exec nginx` in its entrypoint). Graceful shutdown works today, by accident of using the base image properly.

The failure mode to guard against is a future entrypoint that runs nginx as a *child* of a shell — the signal then goes to the shell and nginx is `SIGKILL`ed at the end of the grace period. Step FE-E removes the one custom entrypoint in the repo partly for this reason, and the verification section asserts the behaviour.

This does **not** remove the need for the parent plan's `preStop` sleep: graceful shutdown handles connections nginx already has, while `preStop` covers the window where Traefik still sends *new* connections because Endpoints removal has not propagated yet.

## Per-UI analysis

| UI | Boot-time inputs that can fail | Session-time dependencies | Probe path | Validation required |
| --- | --- | --- | --- | --- |
| `qr-manager-ui` | `config.json` (ConfigMap) — needs `apiBaseURL`, optional `basePath`; `NGINX_BASE_PATH` env | `qr-manager-api` at `apiBaseURL`, called from the browser | `/healthz` | **None today.** Missing ConfigMap → nginx 404s `config.json`, `loadRuntimeConfig` throws, pod stays Ready |
| `homelab-dashboard-ui` | `config.json` (ConfigMap) — needs `unifi.host`, `unifi.apiKey`; `UNIFI_HOST` derived from it for `proxy_pass` | Unifi controller via the pod's own `/proxy/network/` reverse proxy | `/healthz` | Partial — entrypoint fails on missing `unifi.host` only; `unifi.apiKey` unchecked, so a pod with an empty API key boots Ready and every request 401s |

Notes that shape the steps:

- **`homelab-dashboard-ui` already ships `/healthz`, but as a prefix match** (`location /healthz`), so `/healthzabc` also returns `ok`, and it sets the content type with `add_header Content-Type text/plain;` *after* a `return`, which appends a second `Content-Type` header rather than replacing the default. `qr-manager-ui` has no such location at all. Neither app's static fallback `nginx.conf` has one. Four files, four different states — the reason this becomes a shared snippet.
- **`qr-manager-ui`'s probe must be an absolute path.** It is served under `NGINX_BASE_PATH=/qr-manager`, and the probe value in `base.yaml` is a plain `path: /healthz`. `location = /healthz` (exact) is evaluated before the `location ${NGINX_BASE_PATH}/` prefix match, so this holds even when `NGINX_BASE_PATH` is `/`.
- **`homelab-dashboard-ui` is the only image in the repo with a custom `ENTRYPOINT`**, which means it silently opts out of the base image's entrypoint pipeline (IPv6 listener fixup, local resolvers, worker autotune). Converting it back to the stock pipeline is a prerequisite for sharing the validation hook, and is a cleanup in its own right.
- **`replicas: 1` on both.** As the parent plan notes, gapless rollout at one replica comes from `maxUnavailable: 0` + `maxSurge: 1` + a readiness probe the new pod must pass. Fail-fast validation composes correctly with this: a bad ConfigMap CrashLoops the *new* pod while the *old* pod keeps serving. The user sees nothing; the operator sees `CrashLoopBackOff`. That is the desired outcome and it is the strongest argument for fail-fast.

## Key decisions

### 1. Single `/healthz`, exact match, from a shared nginx snippet

Per rule F1. Shipped once in `packages/nginx-runtime` and `include`d by every UI, so the four nginx files cannot drift again.

```nginx
# Kubernetes probe endpoint — liveness, readiness and startup all use this path.
#
# Exact match ("location =") is evaluated before any prefix location, so this
# wins over both "location /" and "location ${NGINX_BASE_PATH}/" — including
# when NGINX_BASE_PATH is "/". The path is deliberately absolute: a probe that
# moved with the base path would need per-app probe values in the helm chart.
#
# default_type (not add_header) sets the content type: with `return`, add_header
# appends a second Content-Type rather than replacing the default.
location = /healthz {
    access_log off;
    default_type text/plain;
    return 200 'ok';
}
```

### 2. One Zod schema, run by a validating initContainer the chart generates

Per rule F3 the config cannot change under a running pod, so one check at start is complete coverage. Per the `replicas: 1` note it is also free: a bad config fails the new pod while the old one keeps serving.

**The schema is written once, in Zod, in TypeScript.** There is no second expression of it in shell, jq, or JSON Schema. The same schema module is:

- bundled into the SPA by Vite and used by `loadRuntimeConfig` in the browser, and
- bundled by esbuild into a ~350 KB minified standalone script run by a **validating initContainer** at pod start (zod inlined; measured, not estimated).

Two build outputs, one source file. That is what separates this from the rejected `jq` designs — those needed validation *semantics* restated in a second language, which is the duplication that rots.

**Why an initContainer and not the nginx entrypoint.** Running the schema in the entrypoint would need a Node runtime inside `nginx:1.29-alpine`. That was drafted and rejected: it is the pattern the Kubernetes documentation explicitly points away from. Init containers exist to hold *"utilities or custom setup code not present in the app image"*, to *"block or delay app container startup until preconditions are met"*, and to *"enhance security by isolating potentially risky tools, thus limiting the attack surface of the app container image"*. All three sentences describe this task exactly.

The decisive cost is not the ~50 MB. It is that a static file server would permanently inherit Node's CVE stream — every image scan flagging a runtime used for 200 ms at startup, forever.

The two objections that made the initContainer look expensive both dissolve once the **chart** generates it rather than a values file declaring it (see the hand-off section):

- *A second tag to keep in lockstep with the SPA.* The chart derives the validator image from the app's own `image.repository` + `-config-validator` and reuses `image.tag` verbatim. The existing `deploy.json` tag bump covers both images with no extra field, and a validator built from a different commit than its SPA is unrepresentable.
- *Values files touching chart internals.* The emptyDir name is built from `include "iot-applications.identifier"`, so a hand-written `initContainers:` block would have to guess it. With the chart generating the container, it already knows the name. The values file says only `validate: true`.

Failure semantics: the initContainer exits non-zero, the pod never reaches the main container, `kubectl get pods` shows `Init:CrashLoopBackOff`, and its logs carry `z.prettifyError()` output naming the offending path.

The nginx image is left exactly as the base image ships it — no Node, no extra packages beyond the `jq` `homelab-dashboard-ui` already uses, `STOPSIGNAL SIGQUIT` and PID 1 untouched (rule F4).

Consequences for the rest of the plan:

- `RUNTIME_CONFIG_REQUIRED_KEYS` is **gone** — no hand-maintained key list in helm values, nothing to drift.
- `packages/nginx-runtime` carries no schema knowledge at all. Its entrypoint hook shrinks to a generic "exists and parses as JSON" guard, kept only so a bare `docker run` without the initContainer still fails loudly.
- One chart change (`templates.<name>.validate`) and one new values key per UI. That is the price of keeping the serving image clean, and it is paid in the repo that already owns chart changes.

**Why not a `/healthz` that validates the config on each request** — the obvious shape, and the one to reach for if nginx could do it. It cannot: nginx has no JSON parser and no scripting. `njs` exists but is a restricted runtime that will not run Zod, so using it means reimplementing the schema — the duplication this decision exists to avoid. Gatekeeping at startup is a *stronger* guarantee anyway: a bad config means the pod never serves at all, rather than serving while reporting itself unhealthy. And per rule F3 the answer cannot change after start, so re-checking per request would burn CPU forever to re-derive a constant.

The other alternative — start nginx, serve `/healthz` 200 and a `/readyz` 503 with a reason — stays rejected: it needs the second endpoint rule F1 argues against, and `CrashLoopBackOff` is a louder, less ambiguous signal in both `kubectl` and the ArgoCD UI than a pod that is Running but has never been Ready.

### 3. The browser does **not** poll the API's `/health/ready`

Worth stating explicitly because it is the obvious-looking way to connect this plan to the backend one, and it is not what the industry does.

Health endpoints are built for infrastructure — kubelet, load balancers, blackbox exporters. The dominant browser-side patterns are different:

- **Failure state is derived from real requests.** Every mainstream data layer (TanStack Query, SWR, RTK Query) models "is the backend up" as a property of the requests the app is already making — `isError`, retry with backoff, an offline/error banner driven by query state. A separate `/health` poll duplicates a signal the app already has and adds a permanent background request per open tab, forever, per user.
- **Connectivity uses `navigator.onLine` and the `online`/`offline` events**, not an application endpoint.
- **Exposing `/health/ready` to browsers widens it.** These endpoints are unauthenticated by necessity (kubelet has no credentials) and the parent plan's rule 3 constrains their body precisely because the ingress exposes them. Making a browser a first-class consumer creates pressure to put useful detail in there — the opposite of what rule 3 wants.

There is one defensible narrow use, and this plan takes it: **recovery detection**. Once a request has already failed, a bounded, backed-off poll that stops the moment it succeeds lets a long-lived tab (a wall-mounted `homelab-dashboard-ui`, say) recover without a human pressing reload. It is opt-in, it only runs while the app is already known-degraded, and it can probe any endpoint the app chooses — the health endpoint is a reasonable default but not a requirement.

So the reusable frontend piece is a **request-driven status model**, not a health poller.

### 4. Two new packages, plus a small addition to `ui-kit`

| Package | Contents | Build | Later |
| --- | --- | --- | --- |
| `packages/nginx-runtime` | `conf.d/healthz.conf`, `docker-entrypoint.d/05-validate-runtime-config.sh` | none — Docker-`COPY`ed assets | `@radoslavirha/nginx-runtime` |
| `packages/ui-runtime` | Headless TS: Zod-driven runtime-config loader, the Node-side validator CLI the initContainer runs, API status model, React hooks | `tsc`/`tsdown` | `@radoslavirha/ui-runtime` |
| `packages/ui-kit` *(existing)* | Gains `<ApiStatusBanner>` — a thin wrapper over the existing `StatusBar` | unchanged | already `@radoslavirha/ui-kit` |

`ui-runtime` is deliberately **headless** — hooks, types and the config loader, no JSX. `ui-kit` stays the single place that owns visuals and `styles.css`. That keeps the dependency arrow one-way (`ui-kit` → nothing, app → both) and means a future non-React experiment can consume the status model without pulling in a component library.

Naming: `ui-runtime` / `nginx-runtime` rather than `ui-health` / `nginx-health`, because both packages own "what this app needs at runtime to be correct" — config loading is the larger half, and health is one consequence of it.

### 5. `loadRuntimeConfig` is consolidated, not just health-adjacent

The two apps have near-duplicate loaders. `qr-manager-ui`'s resolves `config.json` against the `<base href>` nginx injects; `homelab-dashboard-ui`'s always uses `window.location.origin` — which is correct only because it is mounted at the root today, and would break the moment it gets a base path. The config is the thing this whole plan is about validating; having one implementation of loading and validating it, on both sides of the container boundary, is the point.

### 6. Both UIs move to the stock nginx entrypoint pipeline

`homelab-dashboard-ui`'s custom `ENTRYPOINT` is replaced by two `/docker-entrypoint.d/` hooks (the shared validator, plus a small app-specific `.envsh` that derives `UNIFI_HOST`). Benefits: the shared validator works identically in both images, the base image's own init steps come back, and nginx is PID 1 through a code path that is maintained upstream rather than by us (rule F4).

### 7. Validation output must never echo config contents

`homelab-dashboard-ui`'s `config.json` contains `unifi.apiKey`, injected from the `homelab-dashboard-ui-unifi-credentials` secret. The validator reports *which key* failed and *why*, never a value, and never `cat`s the file. Container logs go to Loki.

### 8. `@radoslavirha/resilience` stays backend-only

`packages/resilience` is transport-agnostic and cockatiel-backed with `AbortSignal` support, so reusing it in the SPA is plausible and would satisfy the AGENTS.md "always use toolkit-hub where possible" rule. Deliberately **not** done here: it is built as a dual CJS/ESM Node-oriented package, nobody has measured what it costs a Vite bundle, and the only thing this plan needs from it is backoff for one opt-in recovery probe.

So FE-B6 ships ~30 lines of local backoff behind the `recoveryProbe` option, and the frontend question moves to Follow-ups. Keeping the surface that narrow is what makes the swap cheap later — one call site.

The hook carries **no schema knowledge** — it locates the config and hands it to the app's own bundled validator. That keeps `nginx-runtime` reusable by any UI regardless of what its config looks like.

- [ ] Create `packages/nginx-runtime/docker-entrypoint.d/05-validate-runtime-config.sh`:

```sh
#!/bin/sh
# Validates the rendered runtime config before nginx binds.
#
# The actual rules live in the app's Zod schema, bundled to
# /app/validate-config.js by its Dockerfile stage — this file only locates
# things and reports. Keep it schema-free: the moment it grows per-app
# knowledge, the duplication this design avoids is back (decision 2).
#
# Runs from the stock nginx entrypoint (/docker-entrypoint.d, sorted order,
# `set -e`), so a non-zero exit aborts before nginx binds. Numbered 05 so it
# runs before 20-envsubst-on-templates.sh and any *.envsh that reads the config.
#
# NEVER print config values — homelab-dashboard-ui's config.json holds a secret.
# The validator is responsible for that; see FE-B3.
set -eu

CONFIG_PATH="${RUNTIME_CONFIG_PATH:-/usr/share/nginx/html/config.json}"

fatal() { echo "[nginx-runtime] FATAL: $*" >&2; exit 1; }

[ -f "$CONFIG_PATH" ] \
    || fatal "$CONFIG_PATH not found — the chart mounts it from templates.config."

jq -e . "$CONFIG_PATH" >/dev/null 2>&1 \
    || fatal "$CONFIG_PATH is not valid JSON."

echo "[nginx-runtime] runtime config present and parseable ($CONFIG_PATH)"
```

- [ ] `chmod +x` it, and make the Dockerfile re-apply the bit on `COPY` (the pnpm store and git both preserve the mode, but an explicit `chmod` in the image is cheap insurance).
- [ ] Keep this file schema-free and Node-free. Schema rules live in the validating initContainer (decision 2); the serving image gains nothing beyond `jq`, which `homelab-dashboard-ui` already installs. Pin the `apk` version the way `jq=1.8.1-r0` already is.
- [ ] Note in `packages/nginx-runtime/README.md` that this guard is *not* the real gate — it catches a missing or unparseable file for bare `docker run`, and the initContainer catches everything else. Someone reading only this file must not conclude validation is covered here.

#### FE-A4. Test the guard without a cluster

- [ ] Add `packages/nginx-runtime/test/run.sh` that builds a scratch image `FROM nginx:1.29-alpine` with the hook installed and asserts these cases via `docker run` (the schema cases move to FE-B4, which tests the validator directly in vitest — no Docker needed there):

  | Case | Expected |

  | valid JSON config | exit 0, nginx starts, `/healthz` → `200 ok` |
  | config file absent | container exits non-zero, log names the path |
  | config present but truncated/not JSON | container exits non-zero, log says "not valid JSON" |

- [ ] Assert in the same script that **no config value appears in the container logs** for any case (grep the log for a sentinel secret value planted in the fixture).
- [ ] This is the step that confirms the "stock entrypoint aborts on a failing hook" assumption. If the entrypoint turns out to swallow failures, say so in the README rather than leaving a guard that silently does nothing.

#### FE-B2. Runtime config loader, schema-driven

Zod becomes a real (not peer) dependency of this package — `catalog:` pins it at `4.4.3`, the same version every API and four existing packages already use. This closes the gap `AGENTS.md` already documents: its "Adding a New UI" table specifies `src/runtime/RuntimeConfig.ts` as "`loadRuntimeConfig()` + Zod-equivalent runtime validation", and both UIs hand-rolled string checks instead.

- [ ] `src/config/loadRuntimeConfig.ts` — one implementation replacing both copies, taking the app's Zod schema directly:

```ts
import type { ZodType } from 'zod';

export interface LoadRuntimeConfigOptions<T> {
    /** The app's schema. The same object the validating initContainer runs. */
    readonly schema: ZodType<T>;
    /** Override for tests. Defaults to the <base href>-aware resolver. */
    readonly url?: string;
}

export const loadRuntimeConfig = async <T>(options: LoadRuntimeConfigOptions<T>): Promise<T> => { /* … */ };
```

## Follow-ups

Deliberately out of scope.

- **Serve the SPA shell when the API is down, properly.** Today a failed initial load still renders the app shell; a failed *config* load renders an error box. A service worker or an inlined fallback shell would make the offline story coherent. Meaningful only if these apps are ever used off-LAN.
- **`Cache-Control` and asset immutability.** Vite emits content-hashed assets, but neither nginx config sets `immutable` on `/assets/`, and `index.html` has no explicit no-cache. Adjacent to health (a stale `index.html` referencing deleted asset hashes is a white page that every probe passes) but it is its own change.
- **CSP and security headers.** Both configs ship none. Same file, same review, different plan.
- **External blackbox probing.** The parent plan lists this; for the UIs specifically, a Blackbox Exporter check that the ingress returns HTML containing `<div id="root">` would catch base-path and `<base href>` faults that `/healthz` passes straight through — arguably the highest-value follow-up here.
- **Synthetic monitoring — actually executing the SPA.** Everything in this plan validates *inputs*; nothing proves the app renders. A headless-browser check (Playwright, or k6-browser via Grafana Synthetic Monitoring, which server3's stack already supports) would load the page, run `loadRuntimeConfig`, and assert the app mounted. It is the only check that exercises the JavaScript, so it catches the class config validation structurally cannot: a wrong `NGINX_BASE_PATH`, a cached `index.html` referencing deleted asset hashes, an ingress rewriting the wrong prefix.
- **Feeding a post-start check back into Kubernetes.** If such a check should *gate* a rollout rather than merely alert, three mechanisms exist, in increasing cost:
  1. **ArgoCD PostSync hook Job** — runs after sync; a non-zero exit marks the sync failed and the Application Degraded. No controller to write; cheapest by a distance.
  2. **Argo Rollouts `AnalysisTemplate`** — the mainstream pattern: query Prometheus or run a Job during a canary step and roll back automatically on failure. The chart already renders `rollout.yaml`, but Argo Rollouts is installed in no cluster.
  3. **Pod readiness gates** (`spec.readinessGates`) — the Kubernetes-native way for an external system to withhold pod Readiness via a custom Pod condition, as AWS ALB target-group binding and service meshes do. Requires writing and running a controller; almost certainly not worth it here.

  None of these replaces the validating initContainer. They all run once the pod is already serving, whereas init validation keeps a bad pod out of rotation entirely — they answer different questions and are complementary.
- **`@radoslavirha/resilience` in the browser.** Backend-only today, by decision. If the frontend later wants shared retry / circuit-breaker policy instead of the local backoff in FE-B6, the open questions are whether a package built as dual CJS/ESM for Node tree-shakes acceptably in a Vite build, and what cockatiel costs gzipped. `useApiStatus`'s `recoveryProbe` is the single call site to swap.
- **Bundle-size budget in CI.** A `vite build` size assertion, worth having before adding any runtime dependency to the UIs.

## Alternatives considered

| Option | Verdict |
| --- | --- |
| **`/healthz` + fail-fast config validation at pod start** | **Chosen.** The probe becomes a statement about a container that can actually serve the app, and a bad ConfigMap can no longer produce a Ready pod. |
| `/healthz` alone, as in the parent plan | Rejected as incomplete — it reports on the one thing that cannot fail while ignoring the one thing that does. Kept as the *endpoint* design; extended with layer 2. |
| Separate `/healthz` + `/readyz` for the UIs | Rejected — after boot validation a static file server has nothing to distinguish them (rule F1). Reconsider only if the initContainer proves unworkable, which would force readiness to carry the config signal instead. |
| Start nginx anyway, report the config fault via a 503 on `/readyz` | Rejected — needs the second endpoint, and a permanently-NotReady Running pod is a quieter signal than `Init:CrashLoopBackOff` in both `kubectl` and ArgoCD. |
| Re-validate `config.json` on every probe request | Rejected — the file comes from an emptyDir written once by an initContainer (rule F3), so there is nothing to re-detect. Pure cost. |
| Hand-maintained required-key list in `jq` + a Zod schema in the browser | **Rejected — the duplication that prompted decision 2.** Two expressions of the same rules in two languages, kept in step by discipline. The stricter the browser schema got, the wider the gap, and the gap is precisely "config passes boot, fails in browser, pod is Ready". |
| Generate JSON Schema via `z.toJSONSchema()`, enforce at boot with generic `jq` | Rejected, though closer — one schema source, and the `jq` would be generic rather than per-app. But `jq` can only interpret a subset (`required`, `type`, `minLength`), so `z.url()` and every `.refine()` silently stop being enforced at boot. Partial fidelity is hard to reason about; "the same code runs" is not. |
| Generate JSON Schema, enforce at boot with a static-binary validator (`jv`, `boon`) | Rejected — full JSON Schema fidelity and no Node in the image, but adds a third-party binary to the serving image and still loses `.refine()`, which `z.toJSONSchema()` cannot represent. |
| Node in the nginx image, schema run by the entrypoint | Rejected — no chart change and no second image, but it puts a language runtime into a static file server purely for startup work. The Kubernetes docs point the other way: init containers exist for "utilities not present in the app image", to gatekeep preconditions, and to limit the app image attack surface. The lasting cost is inheriting Node CVEs on a web server forever, not the ~50 MB. |
| A `/healthz` that validates the config on each request | Rejected as impossible in nginx, not merely undesirable — no JSON parser, no scripting. `njs` cannot run Zod, so it would mean reimplementing the schema. Startup gatekeeping is also a stronger guarantee: the pod never serves at all rather than serving while self-reporting unhealthy. |
| **Validating initContainer running the schema, generated by the chart** | **Chosen.** The documented Kubernetes pattern. Deriving the image from the app's own `image` block makes tag lockstep automatic and keeps chart internals out of values files — the two things that made it look expensive in earlier drafts. |
| One shared validator image holding every UI's schema, selected by an arg | Rejected — halves the Dockerfile stages but restores tag drift: a shared image needs its own version, so `qr-manager-ui` 0.6.0 could be validated by a validator pinned at 0.5.x, passing configs the browser then rejects. Per-app images derive their tag from the app's `image.tag`, making a mismatched pair unrepresentable. The two images also share the `node:24-alpine` layer, so the saving would be plumbing only. |
| ArgoCD **PostSync hook Job** running the schema, instead of an initContainer | Rejected for config validation. A hook is a property of one *deployment event*; config validity is a property of the *pod*. It never fires for a Reloader-triggered restart, a node drain, an eviction, an OOMKill or a scale-up — and the Reloader case is precisely "ESO synced an empty secret", the failure this guards. It also runs only after the new pod is Ready, in Endpoints and serving, with the old pod already gone, so it can report but not prevent, and ArgoCD does not auto-roll-back on hook failure. Finally it needs the same validator image, so it saves nothing. Kept in Follow-ups for the *synthetic browser check*, which cannot be an initContainer because the app is not serving at init time. |
| Validating **sidecar** with its own readiness probe | Rejected — same second-image and chart costs as the initContainer, plus a process running for the pod's whole life to re-derive an answer that rule F3 proves cannot change. |
| Replace nginx with a small Node static server that owns `/healthz` | Rejected — would make a live config-aware health endpoint possible, but means reimplementing SPA fallback, base-path handling and `homelab-dashboard-ui`'s Unifi reverse proxy. Far more surface than the problem justifies. |
| Validate in CI / `helm unittest` instead of at pod start | Rejected — the ConfigMap holds Jinja2 *source*; what `{{ SECRET_UNIFI_API_KEY }}` renders to exists only inside the pod (rule F3). CI cannot see the thing that breaks. |
| Readiness probe that fetches the backend API | Rejected — an API outage would empty the UI's Endpoints and turn a degraded page into a Traefik 502 (rule F2). |
| SPA polls the API's `/health/ready` continuously | Rejected — duplicates a signal real requests already carry, adds a forever-request per browser tab, and pushes browser concerns into an endpoint designed for kubelet. See decision 3. |
| SPA polls only while already degraded, to detect recovery | **Accepted, opt-in.** Used by `homelab-dashboard-ui` (unattended screen), not by `qr-manager-ui` (a human is present). |
| `lifecycle.stopSignal: SIGQUIT` in the chart | Rejected as unnecessary — the base image's `STOPSIGNAL SIGQUIT` already applies, and the field needs the `ContainerStopSignals` feature gate plus `spec.os.name`. |
| Keep `homelab-dashboard-ui`'s custom `ENTRYPOINT` and add validation to it | Rejected — it would need the same logic in a second place, and the custom entrypoint silently disables the base image's own init hooks. Converting to `/docker-entrypoint.d/` fixes both. |
| Put the React status model in `ui-kit` | Rejected — `ui-kit` is the presentational layer with no fetch concerns. The headless model lives in `ui-runtime`; only the banner component lands in `ui-kit`. |
| One combined `ui-runtime` package holding the nginx assets too | Rejected — a Docker-`COPY` asset bundle and an npm-consumable React library have different consumers, different build steps and different migration paths to `toolkit-hub`. |
